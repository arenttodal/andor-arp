## 2. Repository architecture

`docs/ARCHITECTURE.md`. OSP stays the single source of the arpeggiator; ANDOR ARP is a separate
repository with OSP as a pinned submodule (never copied), a pure C++ product layer (`shared/`), host
adapters (`max/external`, later `juce/`), and CI that runs the core's own goldens.

## 3. Shared core extraction status — done in OSP (headless verified)

- `andor_arp_core` (OSP `arp-core/`): Arpeggiator, ArpCustomPattern, HostTiming, PatternCapture,
  ArpPatternModel, ArpFactoryPatterns, Prng, and the new pure codec `ArpPatternCodec`. `osp_dsp`
  links it; no file moved, no source compiled twice, no namespace/parameter/plugin ID/stored format
  changed. Builds standalone without JUCE (`cmake -S arp-core`), with an include-isolation test.
- The `.andorpattern` codec's meaning is now in pure C++; OSP's JUCE functions translate `juce::var`
  only. OSP's output is **byte-identical** to the unmodified codec for the 11-document corpus (9
  factory patterns + 2 edge documents), checked against a build of the original code.
- Findings recorded for every implementer: OSP's pattern files have CRLF line ends on all platforms
  (JUCE's `replaceWithText`), and numbers are saved with 6 decimals.
- Results: OSP full ctest on the work branch — see §14; OSP ARP suites (67 cases, 2.4 M assertions,
  18-style golden, CP2/CP3/CP4 engine and model tests) pass; standalone core suite passes;
  ANDOR ANALOG's `analog_dsp_tests` and the core tests pass against the work branch. **Not run:** the
  plugin build's tests on Linux (OSP's macOS CI runs them on push: §14), the ANDOR shell's
  `[shell][arp-custom]` test in ANALOG (blocked by ANALOG's own test drift, known since CP4).

## 5. Ableton one-track routing test results

None. The design (Master → Instrument Rack, a Receiver at the head of each chain) relies on standard
Live behaviour (every chain receives the track's MIDI; a MIDI effect in a chain can replace notes),
but per the spec it is not claimed until demonstrated (M4L-R1..R6).

## 6. Max external and timing results

- External: compiles cleanly against Cycling '74 max-sdk-base `c03a292` (MIT) with the SDK's Linux
  headers; macOS universal build: §14. Not loaded in Max.
- Timing (model only; `docs/results/timing-simulation.md`): 11 scenarios (stale ITM readings, 2–5 ms
  jitter, 20 ms stalls, 100 ppm drift, tempo change, loops with triplets/swing, 1/32 at 48 kHz, clip
  chord changes on bar lines): **0 missing, 0 extra, 0 hanging notes**; deviation after the 4 ms
  output latency ~2 ms mean, ≤ 2 scheduler vectors (~3 ms) except during stalls longer than the
  latency (≤ 17 ms late, never lost). The model found and fixed two design errors (render-ahead
  chord changes; stale anchor).
- **Live measurement not done** (M4L-T1..T4). The spec's rule applies: do not ship before measuring.

## 7. Master/Receiver persistence results

Simulation only (`[link]`, `[blob]`): new Rack pairing, edit routing, reopening with mixed revisions
(newest kept, never overwritten by older), Receivers without a Master keep playing their lanes, a new
Master adopts them, duplicated Rack independence, 30 % message loss, removed and duplicated
Receivers reported. Saved state is checksummed and versioned. **Live persistence (pattr blob in
parameter mode) not verified** (M4L-S1..S4).

## 8. JUCE hosting feasibility results

**Not started.** No hosting code, no DAW, no third-party instrument was tried. `docs/JUCE_IMPLEMENTATION.md`
holds the audit list, the three-slot architecture and the one-slot → three-slot gate. Deferred per the
spec's priority order.

## 9. Known technical blockers

1. **No Mac with Max/Live in this environment:** every Live gate (routing, timing, persistence,
   pairing, freezing) needs the owner's machine or a remote Mac with Live.
2. **Unknowns that decide timing quality:** ITM staleness in Live; `clock_fdelay` resolution; how Live
   time-stamps MIDI from a device inside a chain. The adapter is designed for the pessimistic case; the
   numbers must come from Live.
3. **pattr blob persistence** in a Live Set is assumed, not shown. Fallback if it fails: store the
   state as a hidden `live.*` parameter set (lossy) or in the device's embedded dictionary (verify).
4. **Max UI:** OSP's pattern editor is JUCE; the Master's editor and Capture preview must be rebuilt
   in Max (jsui/v8ui) — the largest remaining effort.
5. **Signing:** the external must be Developer-ID signed and notarised for Gatekeeper; frozen-device
   behaviour with a signed .mxo to be checked.
6. ANDOR ANALOG's own test drift blocks the shell-level ARP test there (pre-existing).

## 10. Risk assessment for a $19 commercial release

| Risk | Level | Why / mitigation |
|---|---|---|
| Musical core quality | low | OSP's arpeggiator with frozen goldens; ANDOR ARP adds no musical code |
| One-track routing in Live | low–medium | standard Rack behaviour; must be demonstrated |
| Timing in Max for Live | **medium** | design proven in a model only; Live's real scheduler/MIDI timestamping unknown |
| Persistence / pairing in Live | **medium** | LOM paths and pattr blob storage unverified; designed fallbacks exist |
| Stuck notes | low–medium | ownership counting + releaseAll proven headless; Live's device deletion/freebang path untested |
| Max UI effort | **medium–high** | the Master UI and Capture editor are new work in Max |
| Support burden (third-party instruments) | low (M4L) | Receivers only send MIDI; the instruments are Live's own chain devices |
| JUCE variant | **high** | nested hosting is a separate product effort; keep deferred |

The Ableton product looks commercially viable at $19 if the Live gates pass with acceptable timing;
the JUCE variant should not be promised.

## 11. Proposed MVP feature freeze (Ableton only)

In: three lanes; the 18 styles; CUSTOM with the 9 factory patterns and library `.andorpattern`
loading; rate, octaves, gate, swing, velocity, STRUM, CONTOUR/DEGREES, transpose, register, mute;
Capture (record → RHYTHM/STEPS → apply); three performance presets; save/recall with the Set; stock
instrument Rack; macOS (universal). Out of V1: the full step editor (EDIT behind a button can come in
1.1), Windows (until the external is built and tested there), the JUCE host, pattern packs, velocity/
microtiming editing (CP6), any account or licensing system.

## 12. Exact next implementation tasks

1. Owner (or a remote Mac with Live): load `andor.arp.engine.mxo` (CI artifact) in Max; build the
   minimal Receiver patch (`max/receiver/README.md`) and run M4L-R1/R2 with three stock instruments.
2. Measure timing (M4L-T1..T4, method in M4L_IMPLEMENTATION §8); compare with the reference; set the
   tolerance; adjust `@latency` if needed.
3. Verify persistence (M4L-S1..S4) with the pattr blob; fall back if needed.
4. Verify pairing (M4L-P1..P4) with `andor-arp-pairing.js`.
5. Build the Master patch with minimal controls (strips: enable, pattern, rate, octaves, gate),
   wire the link; run the full §12 list.
6. Only then: the Master's polished UI (strips, 16-step picture, popovers, Capture preview).
7. Sign/notarise the external; freeze devices; Rack, Set, presets; clean-Mac install test.
8. Merge OSP's `claude/andor-arp-spec-xy4umx` into OSP's line (owner decision), then repoint
   andor-arp's submodule and the core-update workflow at that branch.
9. JUCE: only after the Ableton release, start the one-slot hosting gate.

- **Live + Max on a Mac** (or a remote Mac session) for every Live gate; the owner's instrument

- Decide the acceptable timing tolerance after the Live measurement, and the default `@latency`.
- Developer ID signing for the external (existing ANDOR identity, product-specific bundle id).
